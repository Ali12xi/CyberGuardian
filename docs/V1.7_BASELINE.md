OBSERVATION 5 — Coverage credits are mutually exclusive on header coverage

The three coverage credits cannot all fire together:
- observabilityAwareTransportCredit → requires coverage.headers !== "full"
- observableEdgeHardening → requires coverage.headers !== "full"
- edgeManagedHeaderSurface → requires coverage.headers === "full"

Philosophical interpretation: These represent distinct evidentiary 
regimes — "full visibility" vs "partial/no visibility + edge hardening." 
Likely intentional architectural distinction preventing double-counting 
of inferred trust.

Decision: Documented as semantic discovery. NOT tested as invariant — 
this remains an internal semantic boundary, not external behavior.

OBSERVATION 6 — Limited coverage has no numeric score cap

Score caps work differently for partial vs limited coverage:
- partial → capped at 82 (or 88 with edge hardening)
- limited → no numeric cap applied

Philosophical interpretation: Reflects "not observable ≠ insecure" 
philosophy. Limited observability means we cannot judge with confidence, 
which is epistemically different from partial visibility.

However: formalization may be incomplete. A synthetic contradictory 
input (all stages failed yet healthy ssl/headers fields) can still 
produce a high score — this is a philosophical edge exposure, not 
necessarily a defect.

Decision: Documented as philosophical observation. Article 14 protects 
ONLY graceful degradation (no crash, deterministic, overall === "limited") 
— NOT "limited remains uncapped forever." Future sprints may decide 
on soft caps, confidence attenuation, or degraded ceilings.

OBSERVATION 7 — Redirect layered semantics (same pattern as Day 2)

Same architectural duality as Day 2's Observation 4 (TLS layered 
semantics):
- noRedirectChain positive → keys off redirects.suspicious (deprecated flag)
- threat/penalties → keys off redirects.analysis.intent (structured field)

Philosophical interpretation: Likely architectural evolution — older 
flag-based scoring layer + newer structured semantic layer coexisting. 
Same "claimed vs observed" duality seen in TLS scoring.

Decision: Documented. Article 10 asserts threat only (not score), 
acknowledging the layered semantics without freezing them.

🌐 BILINGUAL DISCIPLINE — dir="ltr" on Value
═══════════════════════════════════════════

Day 3 introduced a small but mature bilingual detail:

```tsx
<p className="bidi-safe min-w-0 text-start">
  {t.server}{" "}
  <span dir="ltr" className="break-all">
    {result.meta.server || t.notDisclosed}
  </span>
</p>
```

Why:
- t.server is bilingual ("Server:" / "الخادم:")
- Server value is always Latin/ASCII technical text

  visually break the server string (e.g. "cloudflare.com" 
  rendering reversed in some browsers)

Result:
- Arabic UI: "الخادم: cloudflare" (label RTL, value LTR)

- Both render correctly across browsers

This is enterprise-grade bilingual maturity in cybersecurity UI 
— rare in the broader market.
